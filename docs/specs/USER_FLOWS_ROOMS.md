### Сценарий 1: Создание комнаты (Владелец)

│                   СОЗДАНИЕ КОМНАТЫ (Alice)                       │

│     │  [💬 1-на-1 чат]        │                                  │
│     │  [🏠 Мои комнаты]       │                                  │
│     │                         │                                  │
│     │  [+ Создать комнату]    │ ← Нажатие                        │
│     └─────────────────────────┘                                  │
│                 │                                                │
│                 ▼                                                │
│  2. НАСТРОЙКА КОМНАТЫ                                            │
│     ┌─────────────────────────┐                                  │
│     │  🏠 Новая комната       │                                  │
│     │                         │                                  │
│     │  ┌───────────────────┐  │                                  │
│     │  │ Название (необяз.)│  │ ← Шифруется клиентом             │

│     │  └───────────────────┘  │                                  │
│     │                         │                                  │
│     │  Режим входа:           │                                  │
│     │  ◉ По паролю            │ ← Вход сразу при верном пароле   │

│     └─────────────────────────┘                                  │

│     └─────────────────────────┘                                  │
│                                                                  │

### Case R1: Неверный пароль комнаты

```
Ситуация: Пользователь ввёл неверный пароль при входе

Поведение:
├── KDF на клиенте → proof не совпадает с хранимым на сервере
├── Сервер возвращает ошибку: INVALID_PROOF
├── UI: "❌ Неверный пароль. Осталось попыток: N"
├── Rate limit: 5 попыток, затем блокировка на 15 мин
└── Сервер НЕ раскрывает, что roomId существует (при неверном токене)
```

### Case R2: Истёкшая инвайт-ссылка

```
Ситуация: Пользователь перешёл по ссылке, но токен expired

Поведение:
├── Сервер: invite:{token} не найден в Redis (TTL истёк)
├── UI: "⏱ Ссылка недействительна или истекла"
├── Рекомендация: "Попросите владельца создать новую ссылку"
└── Никакой информации о комнате не раскрывается
```

### Case R3: Исчерпан лимит использований ссылки

```
Ситуация: Инвайт-ссылка использована maxUses раз

Поведение:
├── Сервер проверяет usedCount >= maxUses (maxUses > 0)
├── Ошибка join/getInviteInfo: INVITE_EXHAUSTED
├── UI: "Ссылка больше не активна"
├── Рекомендация: "Попросите владельца создать новую ссылку"
└── Токен удаляется из Redis (invite:{token} + room_invites:{roomId})
```

**Реализация:** при успешном join `usedCount` инкрементируется атомарно (HINCRBY); при достижении лимита токен удаляется. Владелец может отозвать ссылку досрочно (`/app/room.revokeInvite`) или посмотреть активные (`/app/room.getInvites`).

### Case R4: Максимум участников в комнате

```
Ситуация: В комнате уже 50 участников (лимит)

Поведение:
├── Сервер: room_members:{roomId} size >= MAX_ROOM_MEMBERS
├── UI: "Комната заполнена"
├── Даже владелец не может принять новую заявку
└── Рекомендация: "Дождитесь выхода одного из участников"
```

### Case R5: Владелец offline при заявке

```
Ситуация: Заявка на вход, но владелец не в сети

Поведение:
├── Заявка сохраняется в Redis (TTL 24ч)
├── Telegram Bot отправляет push владельцу:
│   "📨 Новая заявка на вход в комнату"
├── При входе владельца — заявка показывается
└── Если TTL истёк до ответа — заявка удаляется,
    пользователю: "⏱ Заявка истекла"
```

### Case R6: Reconnect к комнате

```
Ситуация: Участник потерял соединение или закрыл/открыл Mini App

Поведение:
├── WebSocket reconnect:
│   ├── REJOIN_ROOM (roomId, tgId)
│   ├── Сервер проверяет membership в room_members:{roomId}
│   └── При успехе: переподписка на топик комнаты
├── Ключи:
│   ├── keyStore в sessionStorage → ключ сохраняется
│   └── Если sessionStorage очищен:
│       ├── Запрос KEY_BUNDLE для текущего epoch
│       └── Расшифровка группового ключа
└── Sync: получение пропущенных сообщений из messages:{roomId}
```

### Case R7: Ротация ключа во время offline

```
Ситуация: Участник был offline, когда кто-то вышел и ключ ротировался

Поведение:
├── При reconnect: участник получает KEY_BUNDLE нового epoch
├── Старые сообщения (до ротации) — расшифровываются старым ключом
│   (если сохранён в keyStore)
├── Новые сообщения — расшифровываются новым ключом
└── Сервер хранит ключи по epoch: room_keys:{roomId}:{epoch}
```

### Case R8: Попытка войти без инвайт-ссылки

```
Ситуация: Пользователь знает roomId, но не имеет токена

Поведение:
├── Без валидного invite-токена нет доступа к комнате
├── Невозможно «найти» комнату по ID или поиском
├── Комнаты не индексируются и не имеют публичного listing
└── Единственный путь — через инвайт-ссылку от владельца
```

### Case R9: Повторный вход после бана

```
Ситуация: Участника забанили; он пытается войти снова по любой инвайт-ссылке

Поведение:
├── Сервер: SISMEMBER room_bans:{roomId} {internalId} → true
├── requestJoin / acceptJoin → USER_BANNED на /user/queue/room-join-result
├── UI: «Вы заблокированы в этой комнате» (room.join.errorBanned)
├── Пароль может быть верным — бан проверяется после proof, но до membership
└── Обход: только разбан владельцем (/app/room.unban) или новая identity
    (новый кошелёк → новый internalId; см. SECURITY.md — ограничение модели угроз)
```

**Реализация:** бан = kick + `SADD room_bans:{roomId}`; список через
`/app/room.getBans` → `/user/queue/room-bans`; разбан fire-and-forget через `/app/room.unban`.

### Case R10: Ошибка бана на стороне владельца

```
Ситуация: Владелец пытается забанить недопустимую цель или превышает rate limit

Поведение:
├── `/app/room.ban` → ROOM_KICK_RESULT success: false
├── Коды: NOT_OWNER, CANNOT_KICK_SELF, CANNOT_KICK_OWNER, NOT_MEMBER,
│   ROOM_NOT_FOUND, RATE_LIMITED, INTERNAL_ERROR (как у KICK_MEMBER)
├── UI: toast с i18n-ключом room.manage.kickError.{code}
└── Банлист и membership не меняются при ошибке
```

### Case R11: Имя забаненного недоступно в UI

```
Ситуация: Забаненный уже удалён из members; владелец открывает «Заблокированные»

Поведение:
├── GET_ROOM_BANS возвращает только internalId[] (без displayName)
├── UI: fallback на internalId + кэш имён из последнего списка участников
│   (resolveBannedLabel в RoomManageView)
└── Разбан доступен по internalId независимо от отображаемого имени
```

## UI/UX Guidelines (Room-specific)

### Отличия от 1-на-1 чатов

| Аспект | 1-на-1 чат | Комната |
|--------|-----------|---------|
| Инициация | Поиск по username | Создание + инвайт-ссылка |
| Вход | Автоматический handshake | Пароль + (заявка) |
| Шифрование | Парный ECDH ключ | Групповой ключ (Sender Keys / Tree-DH) |
| Верификация | Visual Fingerprint | Пароль (zero-knowledge proof) |
| Уничтожение | Любой участник | Только владелец |
| Участники | Ровно 2 | До 50 |
| Роли | Равноправные | Владелец + участники |

### Haptic Feedback Map (Room-specific)

| Действие | Тип Haptic |
|----------|------------|
| Создание комнаты | `success` |
| Вход в комнату | `success` |
| Неверный пароль | `error` |
| Заявка принята | `success` |
| Заявка отклонена | `warning` |
| Burn комнаты | `heavy` + `success` |
| Выход из комнаты | `medium` |
| Получение заявки (владелец) | `light` |
| Бан / кик участника (владелец) | `warning` + `success` (при ack) |
| Попытка входа забаненным | `error` |
| Ротация ключа (скрыто) | — (нет feedback) |

### Состояния комнаты и UI-индикаторы

```
СОЗДАНИЕ      →  🏠 «Комната создана»
ОЖИДАНИЕ      →  ⏳ «Ожидание одобрения»
АКТИВНАЯ      →  🔒 «E2EE активно» + число участников
УНИЧТОЖЕНА    →  🔥 «Комната сжечена»
ИСТЕКЛА (TTL) →  ⏱ «Комната недоступна» (автоудаление)
```

### Навигация

```
ГЛАВНЫЙ ЭКРАН
├── [💬 1-на-1 чат]      → Существующий flow (Phase 1)
├── [🏠 Мои комнаты]     → Список комнат пользователя
│   ├── Карточка комнаты  → Чат комнаты
│   └── [+ Создать]       → Создание комнаты
└── Входящие запросы      → Запросы на 1-на-1 чаты (Phase 1)
```
