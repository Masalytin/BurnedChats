## Обзор

### Цель фазы

Реализовать **комнаты с паролем**, где:

- **Владелец** создаёт комнату, задаёт пароль, генерирует инвайт-ссылки.
- **Участники** входят по ссылке и паролю; при режиме «только по заявкам» — отправляют заявку, владелец принимает или отклоняет.
- **Конфиденциальность**: сервер не хранит пароль в открытом виде; групповой контент — E2EE; метаданные комнаты минимальны.

### Зависимости

- Фаза 1 (MVP) завершена: 1-на-1 чаты, ECDH, AES-GCM, STOMP, Redis, Telegram Auth.
- Документация: [ARCHITECTURE.md](../ARCHITECTURE.md), [DATA_MODELS.md](../DATA_MODELS.md), [SECURITY.md](../SECURITY.md).

## Принципы конфиденциальности

| Аспект | Требование |
|--------|------------|
| **Пароль** | На сервер передаётся только производная (salt + hash/PAKE). Plaintext пароль не логируется и не хранится. |
| **Название комнаты** | Опционально; при хранении — только зашифрованное (ключ от пароля/группового ключа). |
| **Состав участников** | Сервер знает только список Telegram ID в комнате (необходимо для маршрутизации). |
| **Сообщения** | E2EE групповым ключом; сервер — только relay зашифрованных blob'ов. |
| **Инвайт-токены** | Одноразовые или с лимитом использований; не раскрывают roomId без проверки. |
| **Заявки на вход** | Владелец видит только минимальный набор (tgId, username при необходимости); сервер не хранит историю заявок дольше TTL. |

## Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Сложность группового E2EE | Высокая | Высокое | Начать с упрощённой схемы (один групповой ключ, рекей при выходе); Sender Keys позже |
| PAKE для пароля | Средняя | Среднее | MVP: передача proof (salt + hash), rate limit и блокировка по IP при переборе; PAKE в v2.1 |
| Масштаб (много участников) | Средняя | Среднее | Лимит 50 участников; при росте — Tree-DH и оптимизация |
| Deep link Telegram | Низкая | Среднее | Тестировать startapp на раннем этапе; fallback — ручной ввод кода/ссылки |
